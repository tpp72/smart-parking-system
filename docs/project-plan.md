# แผนงานโครงการ: เว็บแอปพลิเคชันระบบการจองและจัดการลานจอดรถอัจฉริยะ (Smart Parking System)

**ประเภทโครงการ:** โครงงานวิชาการ / เว็บแอปพลิเคชัน  
**ระดับ:** ปริญญาตรี สาขาวิทยาการคอมพิวเตอร์  
**สถานะ:** Project Requirement / Project Plan  
**ปรับปรุงล่าสุด:** 2026-09-13 — Deposit/Payment `void`, Walk-in ไม่มีส่วนลด, จองล่วงหน้าไม่เกิน 1 วัน, ยกเลิก Admin สร้าง Reservation, Owner ลาออกต้องอนุมัติ, ยกเลิกสถานะเปิด/ปิดลาน, กรณีลานเต็ม, สิทธิ์ Manual Check-in, ฟิลด์ที่แก้ไข Reservation ได้, Mark as Paid ขณะลานเต็ม  
**เทคโนโลยีหลัก:** Laravel, PHP, PostgreSQL, Blade, Tailwind CSS, Alpine.js, AI Vision API

## 1. บทนำและความเป็นมา

ปัจจุบันการบริหารจัดการที่จอดรถจำนวนมากยังพึ่งพาการบันทึกข้อมูลด้วยมือ เช่น การจดทะเบียนรถ การตรวจสอบช่องจอด การคำนวณค่าจอด และการตรวจสอบข้อมูลย้อนหลัง ซึ่งอาจทำให้เกิดความล่าช้าและความผิดพลาด โดยเฉพาะในช่วงเวลาที่มีรถเข้าใช้บริการจำนวนมาก นอกจากนี้ ผู้ใช้ยังอาจไม่ทราบจำนวนช่องจอดว่างก่อนเดินทาง และเจ้าของลานจอดรถยังต้องใช้เครื่องมือหลายรูปแบบในการติดตามการจอง การเข้า-ออก รายได้ และเหตุการณ์สำคัญของระบบ

โครงการนี้จึงพัฒนาเว็บแอปพลิเคชันสำหรับการจองและจัดการลานจอดรถ โดยรวมกระบวนการตั้งแต่การจัดการลานและช่องจอด การจองล่วงหน้า การชำระเงินมัดจำ การตรวจรถด้วย AI การ Auto Check-in การ Check-out และการคำนวณค่าจอดไว้ในระบบเดียว พร้อมระบบบัญชีดำรถต้องสงสัย การแจ้งเตือน ประวัติการใช้งาน และการจัดการผู้ใช้ตามบทบาท

ระบบออกแบบให้สามารถรองรับการตรวจรถจากกล้องจริงในอนาคต แต่เนื่องจากโครงงานนี้เป็นต้นแบบสำหรับโครงงานจบ การรับภาพรถจะจำลองด้วยการ **Upload รูปภาพ** แทนการเชื่อมต่อกล้องจริง โดยกระบวนการหลังจากรับภาพยังคงจำลองแนวคิดเดียวกับระบบจริง คือ AI วิเคราะห์ภาพแล้วส่งผลเข้าสู่กระบวนการจับคู่ Reservation และ Auto Check-in

## 2. วัตถุประสงค์

1. พัฒนาเว็บแอปพลิเคชันสำหรับบริหารจัดการลานจอดรถและช่องจอดแบบรวมศูนย์
2. พัฒนาระบบจองที่จอดรถล่วงหน้า โดยให้ผู้ใช้ระบุข้อมูลรถในขณะจองและชำระเงินมัดจำเพื่อยืนยันการจอง
3. พัฒนาระบบ Auto Check-in สำหรับทั้งผู้ที่จองล่วงหน้าและผู้ใช้แบบ Walk-in
4. ประยุกต์ใช้ AI Vision เพื่ออ่านข้อมูลจากภาพรถ ได้แก่ ทะเบียน จังหวัด ยี่ห้อ และสี พร้อมใช้ผลลัพธ์ในการจับคู่กับ Reservation
5. พัฒนาระบบจัดการช่องจอดอัตโนมัติ โดยระบบเป็นผู้เลือกช่องจอดให้ผู้ใช้
6. พัฒนาระบบ Check-out และคำนวณค่าจอดตามระยะเวลาที่จอดจริง พร้อมจัดการยอดมัดจำและส่วนลด
7. พัฒนาระบบบัญชีดำรถต้องสงสัยและระบบแจ้งเตือนสำหรับเหตุการณ์สำคัญ
8. พัฒนาระบบแบ่งสิทธิ์ผู้ใช้งาน 3 ระดับ ได้แก่ Admin, Owner และ User
9. พัฒนาระบบ Dashboard, ประวัติ, รายงาน และ Audit Log เพื่อสนับสนุนการบริหารจัดการระบบ
10. ออกแบบระบบให้สามารถต่อยอดไปสู่การรับภาพจากกล้องจริงและระบบ Marketplace ที่ใช้ตำแหน่ง GPS ในอนาคต
11. บังคับให้ผู้ใช้ยืนยันอีเมลก่อนเข้าสู่การใช้งานระบบหลัก
12. บันทึกเหตุการณ์และการกระทำของผู้ใช้งานทุก Role ที่ระบบสามารถตรวจสอบย้อนหลังได้

## 3. ขอบเขตของระบบ

### 3.1 ขอบเขตหลักที่ต้องมีในระบบ

| หมวด               | Requirement                                                                                                                                           |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| ผู้ใช้งาน          | Admin, Owner, User และผู้ใช้ระบบแบบ Walk-in ซึ่งแสดงชื่อเป็น `Walkin User`                                                                            |
| Authentication     | สมัครสมาชิก, Login, Logout, Email Verification, Profile, เปลี่ยนรหัสผ่าน และ Force Password Reset โดย Admin                                           |
| Parking Lot        | จัดการข้อมูลลานจอด กำหนดอัตราค่าจอด และเปิด/ปิดรับ Reservation (ไม่มีสถานะเปิด/ปิดลาน)                                                                            |
| Parking Slot       | เพิ่ม แก้ไข ลบ และสร้าง Slot แบบหลายช่อง พร้อมจัดสถานะและ Lock Slot อัตโนมัติ                                                                         |
| Reservation        | จองล่วงหน้าได้ไม่เกิน 1 วัน เลือกเวลาเริ่มจอด และกรอกข้อมูลรถในขณะจอง                                                                              |
| Deposit            | มัดจำ = ค่าจอด 1 ชั่วโมงตาม `hourly_rate` ของลาน ใช้เพื่อยืนยัน Reservation                                                                           |
| Reservation Expire | หลังถึง `reserve_start` ต้อง Check-in ภายใน 1 ชั่วโมง ไม่เช่นนั้น Reservation หมดอายุและ Slot กลับมาว่าง                                              |
| Auto Check-in      | รับรูป → AI อ่านข้อมูล → จับคู่ Reservation → Auto Check-in หรือสร้าง Walk-in Reservation                                                             |
| Walk-in            | สร้าง Reservation อัตโนมัติโดยใช้ `Walkin User`, เวลาเริ่มปัจจุบัน, มัดจำ 0 และไม่มีส่วนลด `reservation_fee`                                                                         |
| AI Scan            | อ่านทะเบียน จังหวัด ยี่ห้อ สี และ Accuracy จากภาพ                                                                                                     |
| AI Matching        | ทะเบียนต้องตรงทั้งหมายเลขทะเบียนและจังหวัด และยี่ห้อหรือสีต้องตรงอย่างน้อย 1 รายการ                                                                   |
| AI Threshold       | ให้ผลตรวจผ่านเมื่อ Accuracy > 85% ตามเงื่อนไขการประมวลผลของระบบ                                                                                       |
| Blacklist          | ตรวจสอบรถในบัญชีดำด้วยทะเบียน + จังหวัด และแจ้งเตือน Admin/Owner โดยยังอนุญาตให้ Check-in                                                                                   |
| Check-out          | คำนวณค่าจอดจากเวลาจอดจริงและอัตราของลาน                                                                                                               |
| Payment            | บันทึก Deposit Payment และ Checkout Payment โดย Admin/Owner ใช้การยืนยันรับเงิน (`Mark as Paid`) แทนการตรวจสลิปหรือ Payment Gateway ใน Scope ปัจจุบัน |
| Discount           | ใช้ `reservation_fee` เป็นส่วนลดเท่านั้น (= `hourly_rate`) เฉพาะ Reservation ที่มี Deposit                                                                                                              |
| Notification       | แจ้งเตือนเหตุการณ์สำคัญแก่ User, Owner และ Admin ตามสิทธิ์                                                                                            |
| Logs / Reports     | เก็บ Log ทุกประเภทที่ระบบสามารถบันทึกได้ เช่น Reservation, Parking, AI Scan, Payment, Notification และ Audit Log; CSV Export สำหรับ Admin เท่านั้น    |
| Owner Application  | User สามารถสมัครเป็น Owner และรอ Admin พิจารณา; Owner ลาออกต้องได้รับอนุมัติจาก Admin                                                                                                        |
| Dashboard          | แสดงสถานะการจอด การจอง รายได้ และสถิติที่เกี่ยวข้องตาม Role                                                                                           |

### 3.2 ขอบเขตที่วางแผนไว้ภายหลัง

**Marketplace** เป็นฟีเจอร์ที่ตั้งใจพัฒนา แต่จะดำเนินการหลังจาก Core System ได้แก่ Reservation, Auto Check-in, Walk-in, Checkout และ Payment ทำงานครบและเสถียรแล้ว

แนวคิดของ Marketplace:

- แสดงลานจอดที่เปิดใช้งาน
- ใช้ตำแหน่ง GPS ของผู้ใช้เพื่อแนะนำลานจอดใกล้เคียง
- แสดงข้อมูลพื้นฐาน เช่น ชื่อลาน ระยะทาง จำนวนช่องว่าง และอัตราค่าจอด
- ผู้ใช้ที่ยังไม่ Login สามารถดูข้อมูลได้ แต่ต้อง Login ก่อนจอง
- User สามารถเลือกไปยังลานที่ต้องการและเข้าสู่ Flow การจองมาตรฐาน

Marketplace **ไม่ใช่ส่วนที่ต้องนำมาเป็นเงื่อนไขหลักของ Core Flow ในระยะแรก** และไม่ควรทำให้การพัฒนาหรือการทดสอบ Reservation/Check-in ต้องรอ Marketplace

### 3.3 สิ่งที่ไม่อยู่ในขอบเขต

- การเชื่อมต่อกล้องตรวจรถจริงในโครงงานนี้ โดยใช้ Upload รูปแทนเพื่อจำลอง Hardware Input
- Hardware สำหรับเปิด-ปิด Barrier Gate
- Mobile Application แบบ Native สำหรับ iOS/Android
- การรายงานภาษีหรือเอกสารบัญชีเชิงลึก
- การตรวจสอบสลิปโอนเงินหรือระบบ Payment Gateway/QR Payment ภายนอกใน Scope ปัจจุบัน
- ระบบ Payment Gateway/QR Payment ที่เชื่อมต่อผู้ให้บริการภายนอกแบบ Production
- ระบบ Promotion แบบเต็มรูปแบบ
- Coupon
- Discount Code
- ระบบ Vehicle Registration หรือการเก็บข้อมูลรถเป็น Entity แยกต่างหากแบบระบบเดิม
- ฟังก์ชันหรือ Flow เก่าที่ถูกแทนที่ด้วย Plate-based Reservation

- ระบบ Role/Permission แบบแยก `Role` / `Permission` Model; ให้ใช้ `users.role` เป็นกลไก Role หลัก
- การให้ Admin สร้าง Reservation แทน User แบบ Manual
- สถานะเปิด/ปิดลาน (ลานมีเฉพาะสถานะเปิด/ปิดรับ Reservation)

## 4. หลักการข้อมูลรถของระบบใหม่

ระบบใหม่ใช้แนวคิด **Plate-based** เป็นหลัก โดยไม่มีขั้นตอนให้ User ลงทะเบียนรถไว้ล่วงหน้าเป็น Vehicle Entity

> **แก้ไข 2026-09-27:** ผู้ใช้ **ผูกทะเบียนกับบัญชีได้โดยสมัครใจ** (§4.0.3) เพื่อให้รถที่เข้าลานแบบ Walk-in
> ผูกกับบัญชีเจ้าของอัตโนมัติ — **ไม่ใช่เงื่อนไขบังคับก่อนจอง** การจองยังกรอกทะเบียนตอนจองเหมือนเดิมทุกอย่าง
> และไม่ได้กลับไปเป็น Vehicle Entity เดิมที่ต้องลงทะเบียนรถก่อนใช้งานระบบ

ข้อมูลรถจะถูกบันทึกในขั้นตอน Reservation หรือ Walk-in ประกอบด้วย:

- `license_plate` — หมายเลขทะเบียนรถ
- `plate_province` — จังหวัดของทะเบียน
- `brand` — ยี่ห้อรถ (เลือกจาก `config/car_brands.php`)
- `color` — สีรถ (เลือกจาก `config/car_colors.php`)

ทั้ง **ยี่ห้อ จังหวัด และสี** เป็นรายการปิด — ผู้ใช้เลือกจาก dropdown และ Claude Vision ถูกสั่งให้ตอบจากรายการเดียวกัน
จึงเทียบกันแบบ exact match ได้ตรง (ยี่ห้อเทียบแบบไม่สนตัวพิมพ์เล็กใหญ่) · รายการยี่ห้ออ้างอิงยอดจดทะเบียนจริงในไทย
และมี "อื่น ๆ" ปิดท้ายให้รถที่ยี่ห้อไม่อยู่ในรายการยังจองได้ — กรณีนั้นระบบยังจับคู่ด้วยสีได้ตามกติกา "ยี่ห้อหรือสี"

#### 4.0 ที่อยู่ของลานจอด (กำหนด 2026-09-24)

ที่อยู่เลือกเป็นชั้นตามเขตการปกครองไทย **จังหวัด → อำเภอ/เขต → ตำบล/แขวง** แล้วระบบเติม **รหัสไปรษณีย์** ให้เอง

- ข้อมูลอยู่ที่ `public/data/thai-geography.json` ไฟล์เดียว (77 จังหวัด · 928 อำเภอ/เขต · 7,436 ตำบล/แขวง)
  ใช้ร่วมกันทั้งเซิร์ฟเวอร์ (`App\Support\ThaiGeography`) และเบราว์เซอร์ (dropdown ที่ขึ้นต่อกัน)
- รหัสไปรษณีย์ผูกกับ **ตำบล/แขวง** จึงเติมได้ต่อเมื่อเลือกครบทั้ง 3 ชั้น · ช่องรหัสเป็น read-only
- **เซิร์ฟเวอร์คำนวณรหัสไปรษณีย์ใหม่เองเสมอ** ไม่รับค่าที่ส่งมาจากฟอร์ม
- `App\Rules\ExistingThaiAddress` ตรวจว่าชุด จังหวัด+อำเภอ+ตำบล อยู่ใต้กันจริง (ผูกที่ช่องตำบล/แขวง)
- คำขอเปิดลานจอด: ที่อยู่**บังคับครบ 3 ชั้น** · ลานจอด: ที่อยู่ไม่บังคับ แต่ถ้ากรอกต้องครบ (`required_with:province`)
- คอลัมน์ใหม่ `subdistrict` (100) และ `postal_code` (5) ทั้ง `parking_lots` และ `owner_applications` เป็น nullable
  ข้อมูลเดิมที่ยังไม่มีตำบลจึงไม่พัง

#### 4.0.1 รหัสอ้างอิงของรถ Walk-in (กำหนด 2026-09-24 · Phase 1)

รถที่เข้าแบบ Walk-in ไม่มีบัญชีผู้ใช้ผูกอยู่ (เจ้าของรายการคือบัญชีระบบ `Walkin User`)
คนขับจึงไม่มีทางดูได้เองว่ารถจอดช่องไหน ค่าจอดเท่าไร ต้องเดินไปถามเจ้าหน้าที่อย่างเดียว

- ตอน Check-in แบบ Walk-in ระบบออก **รหัสอ้างอิง 6 ตัว** เก็บที่ `reservations.reference_code` (unique)
- ชุดอักขระตัด `0 O 1 I L` ออก เพราะคนขับต้องอ่านจากจอแล้วพิมพ์เอง — เหลือ 31 ตัว × 6 หลัก ≈ 887 ล้านแบบ
- สุ่มด้วย `random_bytes` ไม่ใช่ `rand` เพราะรหัสนี้ทำหน้าที่เป็นหลักฐานยืนยันตัวคนขับ
- **การจองล่วงหน้าไม่ออกรหัส** (`reference_code` เป็น null) เพราะเจ้าของบัญชีดูในหน้าหลักของตัวเองได้อยู่แล้ว
- แสดงบนหน้าผลสแกน **ในบล็อกเดียวกับเลขช่องจอด** — ในลานจริงคือจอที่ทางเข้าที่แสดงช่องจอดคู่กับรหัสนี้

เหตุผลที่ต้องมีรหัส ไม่ใช้แค่ทะเบียน: ป้ายทะเบียนเห็นได้จากภายนอก ถ้าใช้ทะเบียนอย่างเดียวเป็นกุญแจ
ใครก็ตามที่เห็นป้ายจะตามดูได้ว่ารถคันนั้นจอดอยู่ลานไหน ช่องไหน ตั้งแต่กี่โมง

#### 4.0.2 หน้าเช็คสถานะรถโดยไม่ต้องล็อกอิน (กำหนด 2026-09-27 · Phase 2)

`GET /track` · `POST /track` — หน้าสาธารณะ ไม่ต้องเข้าสู่ระบบ

- ยืนยันตัวด้วย **ทะเบียน + จังหวัด + รหัสอ้างอิง** ครบทั้ง 3 อย่างเท่านั้น
- ใช้ได้ทั้งรถ Walk-in และรถที่จองล่วงหน้า — **ออกรหัสให้ทุกคันตอน Check-in** ไม่ใช่เฉพาะ Walk-in
  เพราะคนขับอาจไม่ใช่เจ้าของบัญชีที่จองไว้ · ออกครั้งเดียว ไม่เปลี่ยนถ้ามีอยู่แล้ว
- แสดง: ป้ายทะเบียน · ลานจอด · ช่องจอด · เวลาเข้าลาน · จอดมาแล้ว · **ค่าจอด ณ ตอนนี้**
  (คำนวณด้วย `CheckOutService::calculate()` ตัวเดียวกับตอน Check-out จริง)
- **ไม่แสดง:** ชื่อเจ้าของบัญชี · อีเมล · ประวัติครั้งก่อน · ข้อมูลรถคันอื่น
- แสดงเฉพาะรถที่ `status = checked_in` และยังไม่ Check-out
- ข้อความเมื่อหาไม่เจอ **เหมือนกันทุกกรณี** ไม่บอกว่าผิดที่ทะเบียนหรือรหัส เพื่อไม่ให้ใช้หน้านี้ไล่เดา
- `throttle:10,1` ต่อ IP — รหัสอ้างอิงเป็นหลักฐานยืนยันตัว ต้องกันการสุ่ม

#### 4.0.3 ผูกทะเบียนรถกับบัญชี (กำหนด 2026-09-27 · Phase 3)

ตาราง `user_vehicles` (`user_id`, `license_plate`, `plate_province`) · **1 ทะเบียนในจังหวัดนั้นผูกได้กับบัญชีเดียว**

**การผูกต้องมีหลักฐาน** — ผูกได้ทางเดียวคือเช็คสถานะรถที่ `/track` ด้วยรหัสอ้างอิงสำเร็จก่อน
ระบบจำไว้ใน session ว่าผู้ใช้คนนี้พิสูจน์แล้วว่าอยู่กับรถคันนั้น แล้วจึงผูกได้ · **หลักฐานใช้ได้ครั้งเดียว**
เหตุผล: ป้ายทะเบียนเห็นได้จากภายนอก ถ้าผูกได้โดยไม่มีหลักฐาน ใครก็อ้างว่ารถคันไหนเป็นของตัวเองก็ได้

**ผลเมื่อผูกแล้ว** — รถคันนั้นเข้าลานโดยไม่ได้จองล่วงหน้า:

| | ก่อนผูก | หลังผูก |
| --- | --- | --- |
| เจ้าของรายการ | บัญชีระบบ `Walkin User` | **บัญชีของผู้ใช้** |
| `is_walk_in` | true | **true (ไม่เปลี่ยน)** |
| มัดจำ / ส่วนลด | 0 / 0 | **0 / 0 (ไม่เปลี่ยน)** |
| ค่าจอด | เต็มจำนวนตามเวลาจริง | **เต็มจำนวนตามเวลาจริง (ไม่เปลี่ยน)** |
| การแจ้งเตือน | ไม่มีใครรับ | **เจ้าของได้รับทั้งตอนเข้าและออกจากลาน** |
| เห็นในหน้าหลัก / ประวัติ | ไม่เห็น | **เห็น** |

**การผูกรถไม่เปลี่ยนวิธีคิดเงินใด ๆ** — เปลี่ยนแค่ว่ารายการเป็นของใคร และใครได้รับการแจ้งเตือน

- จัดการรถที่ผูกไว้ที่หน้าโปรไฟล์ (เฉพาะบทบาทผู้ใช้) — เพิ่มจาก `/track` เท่านั้น · นำออกได้ตลอด
- นำรถออกไม่กระทบประวัติการจอดเดิม
- บันทึก Audit Log ทั้งตอนผูก (`user_vehicle.link`) และนำออก (`user_vehicle.unlink`)
- ทะเบียนเทียบแบบไม่สนตัวคั่น ใช้ตัวเทียบเดียวกับทั้งระบบ (§4.1)

#### 4.1 รูปแบบมาตรฐานของเลขทะเบียน (กำหนด 2026-09-23)

ทุกทางเข้า (ผู้ใช้กรอก · AI อ่าน · บัญชีดำ · Walk-in) ผ่าน `App\Support\LicensePlateNormalizer` ตัวเดียวกัน
**ไม่ใช่ตัวตรวจว่าทะเบียนถูกต้องตามกฎหมาย** — ประกาศกรมการขนส่งทางบกเปิดให้ป้ายลักษณะพิเศษมีตัวอักษรมากกว่า 2 ตัว
หรือผสมสระ/วรรณยุกต์ได้ ระบบจึงไม่ปฏิเสธทะเบียนเพราะไม่ตรงรูปแบบที่คาดไว้

**ตัวคั่นมาตรฐานคือช่องว่าง 1 ตัว** · ฐานข้อมูลเก็บค่านี้ และหน้าจอแสดงค่าเดียวกัน ไม่มีรูปแบบสำหรับแสดงผลแยกต่างหาก

| ผู้ใช้/AI ส่งมา | เก็บและแสดงเป็น |
| --- | --- |
| `กข1234` · `กข-1234` · `กข  1234` · `กข - 1234` | `กข 1234` |
| `1กข1234` · `1กข-1234` | `1กข 1234` |
| `43-8633` (รถบรรทุก/รถโดยสาร) | `43 8633` |
| `กข๑๒๓๔` (เลขไทย) | `กข 1234` |
| `น่ารัก 9999` · `น่ารัก9999` (ป้ายลักษณะพิเศษ) | คงรูปเดิม ไม่เดาตำแหน่งตัวคั่น |

- `normalize()` — ค่าที่บันทึก: NFC · ยุบตัวคั่นทุกชนิดเหลือช่องว่างเดียว · เลขไทยเป็นเลขอารบิก · อักษรละตินเป็นตัวพิมพ์ใหญ่
  · เติมช่องว่างให้เฉพาะรูปแบบที่ขอบเขตหมวดกับเลขชัดเจน (พยัญชนะไทยหรืออักษรละตินล้วน ตามด้วยตัวเลข)
- `comparisonKey()` — กุญแจจับคู่: ถอดเฉพาะตัวคั่นออก ไม่แตะสระ วรรณยุกต์ หรืออักขระอื่น
- **การจับคู่ทุกจุดใช้ `comparisonKey`** — AI จับคู่การจอง · บัญชีดำ · รถที่จอดอยู่ · กันจองซ้ำ · ช่องค้นหา
  กติกาการจับคู่เดิมไม่เปลี่ยน: `ทะเบียน + จังหวัด` และ `ยี่ห้อหรือสีอย่างน้อย 1 อย่าง`
- `isRecognizableFormat()` บอกได้แค่ว่าระบบแยกหมวดกับเลขได้หรือไม่ **ห้ามใช้เป็นเงื่อนไขปฏิเสธการบันทึก**
- ความยาวสูงสุด 20 ตัวอักษรเท่ากันทุกทางเข้า (ตรงกับ `varchar(20)` ของฐานข้อมูล)

**การกันข้อมูลมั่ว (`App\Rules\PlausibleLicensePlate`, กำหนด 2026-09-24)**

ฟอร์มที่ผู้ใช้กรอกเอง (จองรถ · แก้ข้อมูลรถ · บัญชีดำ) ปฏิเสธค่าที่เป็นทะเบียนไม่ได้ เช่น `ฟ้าพฟฟด`
โดยใช้เงื่อนไขเชิงโครงสร้าง 3 ข้อที่ทะเบียนทุกประเภทผ่านได้ **ไม่ใช่การบังคับรูปแบบ**:

1. มีตัวเลขอย่างน้อย 1 ตัว — ทุกรูปแบบมีเลขทะเบียนเสมอ (`กข 1234` · `น่ารัก 9999` · `งาม 1` · `43 8633`)
2. ใช้เฉพาะอักษรไทย (รวมสระ/วรรณยุกต์) อักษรละติน ตัวเลข และช่องว่าง
3. ยาว 2–20 ตัวอักษร

ผลที่ตามมาที่ต้องรู้: ถ้ามีทะเบียนที่**ไม่มีตัวเลขเลย** ระบบจะปฏิเสธ — จากรูปแบบที่กรมการขนส่งทางบกประกาศไว้
ยังไม่พบกรณีแบบนั้น ถ้าเจอในอนาคตให้แก้เงื่อนไขข้อ 1

ฝั่งหน้าเว็บตัดอักขระนอกข้อ 2 ทิ้งระหว่างพิมพ์ ส่วนเงื่อนไข "ต้องมีตัวเลข" ตรวจที่เซิร์ฟเวอร์เท่านั้น
เพื่อไม่ขัดจังหวะขณะพิมพ์ · AI Scan และ Walk-in **ไม่ผ่านกฎนี้** เพราะไม่ควรทิ้งผลการอ่านของกล้อง

### ตัวตนของ Walk-in

Walk-in ใช้ **System User ชื่อ `Walkin User`** เป็นตัวแทนในระบบ โดยเป็น User record พิเศษที่ใช้สำหรับเชื่อมโยง Reservation, Parking Log, Payment และ Log ต่าง ๆ ของรถที่เข้ามาแบบ Walk-in

ข้อกำหนด:

- ใช้ `user_id` ของ System User นี้กับ Reservation ของ Walk-in
- ชื่อที่แสดงในระบบเป็น `Walkin User`
- เป็นบัญชีสำหรับระบบ ไม่ใช่บัญชีลูกค้าปกติ
- **ไม่อนุญาตให้ Login เพื่อใช้งานระบบในฐานะผู้ใช้จริง**
- Walk-in ไม่ต้องมีการสมัครสมาชิกหรือ Email Verification ของตนเอง
- เป็น record ในตาราง `users` โดยใช้ `role = user` (ไม่ใช่ Role ใหม่)
- `Walkin User` **ไม่ได้รับ Notification**

ข้อมูลดังกล่าวเป็นข้อมูลของ Reservation/การเข้าจอดในแต่ละรายการ ไม่ใช่ข้อมูลรถถาวรของ User

### 4.1 กรณี User จองล่วงหน้า

User กรอกข้อมูลรถในขณะสร้าง Reservation และสามารถแก้ไขข้อมูลรถของ Reservation ได้ก่อน Auto Check-in/Check-in ตามกฎของสถานะ Reservation

ฟิลด์ที่แก้ไขได้: **ทะเบียนรถ จังหวัด สีรถ และยี่ห้อรถ** เท่านั้น — แก้ไข Parking Lot และ `reserve_start` ไม่ได้

### 4.2 กรณี Walk-in

Walk-in ไม่มี Reservation เดิม แต่ระบบจะสร้าง Reservation ขึ้นใหม่โดยอัตโนมัติ แล้วใช้ Flow เดียวกับ Reservation ปกติ

ข้อมูลหลักของ Walk-in:

- User/ผู้ครอบครองรายการ = `Walkin User`
- `reserve_start` = เวลาปัจจุบัน
- Deposit = 0
- ไม่มีส่วนลด `reservation_fee`
- สถานะ Reservation = `checked_in` ทันทีเมื่อ Auto Check-in สำเร็จ
- ข้อมูลรถ = ข้อมูลที่ได้จาก AI หรือข้อมูลที่ระบบรับเข้ามาตามขั้นตอน Walk-in

## 5. บทบาทผู้ใช้งานและสิทธิ์

ระบบมี 3 Role หลัก ได้แก่ **Admin, Owner และ User**

### 5.1 Admin — ผู้ดูแลระบบระดับสูงสุด

Admin เป็นผู้ดูแลเว็บไซต์และระบบโดยรวม แต่การเป็นผู้ดูแลระบบ **ไม่ได้หมายความว่า Admin เป็นเจ้าของทุกลาน**

#### Dashboard และภาพรวม

- ดูจำนวนรถที่กำลังจอด
- ดูจำนวน Slot ว่าง/ถูกจอง/ถูกใช้งาน
- ดู Reservation ที่อยู่ในสถานะต่าง ๆ
- ดูรายได้และสถิติของระบบ
- ดูข้อมูลสำคัญจากทุกลานในขอบเขตของ System Administration

#### จัดการ Parking Lot ของ Admin

- เพิ่ม/แก้ไข/ลบลานที่เป็นของ Admin
- กำหนดชื่อและข้อมูลลาน
- กำหนดที่อยู่ รายละเอียด และจุดสังเกต
- กำหนด `hourly_rate`
- เปิด/ปิดรับ Reservation
- จัดการ Slot ของลานที่เป็นของ Admin

ลานของ Admin คือลานที่ `owner_id = NULL` และ Admin ทุกคนใช้ลานกลุ่มนี้ร่วมกัน

**หมายเหตุ:** Admin ไม่ควรแก้ไขข้อมูล Parking Lot ของ Owner โดยอัตโนมัติเพียงเพราะเป็น System Administrator เว้นแต่ Requirement ของฟังก์ชันระดับระบบนั้นกำหนดไว้โดยตรง

#### ระบบ Reservation

- ดู Reservation ในระดับระบบ
- ค้นหาและกรองตามข้อมูลที่เกี่ยวข้อง
- ดูสถานะ Reservation
- ตรวจสอบประวัติและเหตุการณ์ของ Reservation
- **Admin ไม่สามารถสร้าง Reservation แบบ Manual** — Reservation เกิดจาก User จองเอง หรือจาก Walk-in Flow เท่านั้น
- Admin ไม่ใช้กระบวนการ Manual Confirm แบบเดิม; การยืนยัน Reservation ต้องอ้างอิงผลการชำระ Deposit และการยืนยันรับเงิน (`Mark as Paid`) ตาม Payment Flow
- ดำเนินการที่ระบบกำหนดให้ Admin ทำได้ เช่น ยกเลิกหรือจัดการเหตุผิดปกติ
- Manual Check-in กับรถที่เข้าลานของ Admin (`owner_id = NULL`) เมื่อ Auto Check-in ดำเนินการไม่ได้

#### ระบบ User

- ดูและค้นหาผู้ใช้
- กรองตาม Role
- จัดการ Role ตามสิทธิ์ของระบบ
- Force Password Reset
- ดูข้อมูลบัญชีที่เกี่ยวข้องกับระบบ

#### Owner Application

- ดูคำขอสมัคร Owner
- อนุมัติหรือปฏิเสธ
- ระบุเหตุผลกรณีปฏิเสธ
- ตรวจสอบข้อมูล/เอกสารที่เกี่ยวข้อง
- รองรับการจัดการสถานะ Owner ตาม Flow ของระบบ
- อนุมัติหรือปฏิเสธคำร้องลาออกของ Owner

#### AI Scan / Blacklist

- ใช้งาน AI Scan
- ดูผล Scan และข้อมูล Accuracy
- จัดการบัญชีดำ
- ดูเหตุการณ์ AI ที่ไม่ผ่านเกณฑ์
- รับและตรวจสอบการแจ้งเตือนจากระบบ

#### Payment

- ดูรายการ Payment
- ตรวจสอบรายการค้างชำระและชำระแล้ว
- ยืนยันสถานะการรับชำระตามสิทธิ์ที่ระบบกำหนด

#### Logs / Reports

- ดู Reservation Log
- ดู Parking Log
- ดู Audit Log
- Export ข้อมูลที่ระบบรองรับ เช่น CSV
- ตรวจสอบเหตุการณ์สำคัญของระบบ

#### 5.1.1 รายละเอียดที่กำหนดเพิ่ม (2026-09-14)

- **Admin Dashboard แสดงข้อมูลทั้งระบบ ทุกลาน** (รถที่จอด, Slot, Reservation แยกสถานะ, รายได้, จำนวนลาน, สถิติ AI Scan, Blacklist) — รายได้ใช้นิยาม "เงินที่รับจริง" เดียวกับฝั่ง Owner (§16.1)
- **หน้าจัดการ** (Reservation / Payment / Parking Log / Parking Lot / Slot) ยังจำกัดเฉพาะลานของ Admin (`owner_id = NULL`)
- **Role:** การเป็น Owner ต้องผ่านคำขอสมัคร Owner เท่านั้น — Admin สร้างหรือเปลี่ยนผู้ใช้เป็น Owner โดยตรงไม่ได้ และอนุมัติคำขอได้เฉพาะผู้สมัครที่เป็นบัญชี User
- **ตั้ง Admin คนใหม่:** Admin สร้างบัญชี Admin ใหม่ หรือเปลี่ยน User เป็น Admin ได้ (บัญชีใหม่ถูกบังคับเปลี่ยนรหัสผ่านเมื่อเข้าครั้งแรก) · เปลี่ยนบทบาทของบัญชีตัวเองออกจาก Admin ไม่ได้ เพื่อไม่ให้ระบบเหลือ 0 ผู้ดูแล
- **ปลด Owner → User:** ต้องระบุเหตุผล และระบบปิดลานทั้งหมดของ Owner แบบเดียวกับอนุมัติคำร้องลาออก (§16) — คำร้องลาออกที่ค้างอยู่ถือว่าดำเนินการแล้ว; Owner เปลี่ยนเป็น Admin โดยตรงไม่ได้
- **ลบผู้ใช้:** ระบบยกเลิกการจองที่ยังไม่ Check-in และเช็คเอาท์รถที่จอดอยู่ของผู้ใช้ก่อน (คืนช่องจอด) ถ้าเป็น Owner ปิดลานทั้งหมดก่อน แล้วจึงลบบัญชี; ลบบัญชีตัวเองไม่ได้
- **ลานของ Admin:** กำหนดหรือโอนเจ้าของลาน (`owner_id`) ไม่ได้ และลบไม่ได้ถ้ายังมีการจอง `pending` / `confirmed` / `checked_in`
- **บัญชีระบบ** (`Walkin User`) ไม่แสดงในหน้าจัดการผู้ใช้ และแก้ไข/รีเซ็ตรหัสผ่าน/ลบไม่ได้

## 6. ระบบ Parking Lot และ Parking Slot

### 6.1 Parking Lot

แต่ละลานต้องมีข้อมูลอย่างน้อย:

- ชื่อลาน
- ข้อมูลที่อยู่
- รายละเอียด/จุดสังเกต
- `hourly_rate`
- สถานะเปิด/ปิดรับ Reservation
- เจ้าของลาน (`owner_id`) — `NULL` หมายถึงลานของ Admin

ข้อกำหนด:

- ลาน **ไม่มีสถานะเปิด/ปิดลาน** มีเพียงสถานะเปิด/ปิดรับ Reservation ซึ่งมีผลกับการจองล่วงหน้าเท่านั้น
- Walk-in เข้าได้ทุกลานที่มี Slot ว่าง โดยไม่ขึ้นกับสถานะเปิด/ปิดรับ Reservation
- เมื่อลบลาน ข้อมูลที่ผูกกับลาน (Slot, Reservation, Parking Log, Payment และข้อมูลที่เกี่ยวข้อง) จะถูกลบตามไปด้วย

### 6.2 Parking Slot

ระบบต้องรองรับการสร้าง Slot:

- ทีละช่อง
- หลายช่องพร้อมกัน (Bulk Create)

ระบบต้องจัดการ Slot ตามสถานะการใช้งาน เช่น:

- `available` — ว่าง
- `reserved` — ถูกจอง/Lock สำหรับ Reservation
- `occupied` — มีรถจอดอยู่

### 6.3 กฎสำคัญของ Slot

1. User **เลือกได้เฉพาะ Parking Lot** และไม่สามารถเลือก Slot เอง
2. ระบบเป็นผู้จัดสรร Slot ให้โดยอัตโนมัติ
3. Slot ที่ `occupied` ไม่สามารถถูกจองหรือจัดสรรให้ Reservation ใหม่ได้
4. ระบบจัดสรรและ Lock Slot (`reserved`) ให้ Reservation **เมื่อ Deposit ได้รับการยืนยันรับเงิน (Mark as Paid) แล้วเท่านั้น** — Reservation ที่ยัง `pending` ไม่ถือครอง Slot และ Slot ที่ Lock แล้วห้าม Reservation อื่นใช้ซ้ำ
5. เมื่อ Reservation ถูกยกเลิกหรือ Expire ก่อน Check-in ระบบต้องคืน Slot ให้พร้อมใช้งาน
6. เมื่อรถ Check-in ระบบเปลี่ยน Slot เป็น `occupied`
7. เมื่อ Check-out ระบบเปลี่ยน Slot กลับเป็น `available`
8. ห้ามลบ Slot ที่กำลังมีรถจอดอยู่
9. การจอง Slot ต้องป้องกัน Race Condition ด้วย Transaction/Database Lock ตามที่เหมาะสม
10. หมายเลข Slot ต้องไม่ซ้ำกันภายในลานเดียวกัน (`parking_lot_id` + `slot_number`)
11. ลานที่ไม่มี Slot ว่างจะไม่แสดงให้ User เลือกจอง
12. ถ้าขณะยืนยันรับเงิน Deposit ไม่มี Slot ว่าง ระบบยกเลิก Reservation และแจ้งเตือน User (ดู §13.2)

## 7. ระบบ Reservation

### 7.1 การสร้าง Reservation

User ต้องระบุ:

- Parking Lot
- เวลาเริ่มจอด (`reserve_start`)
- เลขทะเบียน
- จังหวัด
- ยี่ห้อ
- สี

Reservation **ไม่มีเวลา Check-out ที่กำหนดล่วงหน้า** และ **ไม่มี `reserve_end` เป็นเวลาที่ผู้ใช้เลือก**

ข้อกำหนดเพิ่มเติม:

- ทะเบียน + จังหวัดเดียวกันมี Reservation ที่ยัง Active (`pending`, `confirmed`, `checked_in`) ได้เพียง 1 รายการ (ไม่นับ Walk-in — §10.10)
- Reservation ถูกสร้างโดย User หรือโดยระบบผ่าน Walk-in Flow เท่านั้น — **Admin ไม่สามารถสร้าง Reservation แบบ Manual**

### 7.2 กฎเวลา

- สามารถจองล่วงหน้าได้ **ไม่เกิน 1 วัน (24 ชั่วโมงนับจากเวลาที่ทำการจอง)**
- ห้ามเลือกเวลาในอดีต
- หลังถึง `reserve_start` ต้อง Check-in ภายใน **1 ชั่วโมง**
- เมื่อเกิน 1 ชั่วโมงและยังไม่ Check-in → Reservation เป็น `expired`
- เมื่อ Expire → Slot ที่ Lock ไว้ต้องกลับเป็น `available`

### 7.3 สถานะ Reservation

สถานะหลักที่ระบบควรรองรับ:

```text
pending → confirmed → checked_in → completed
                    ↘ cancelled
                    ↘ expired
```

ความหมาย:

- `pending` — สร้าง Reservation แล้วและอยู่ระหว่างการดำเนินการชำระ/ยืนยัน Deposit
- `confirmed` — Deposit ได้รับการชำระและ Admin/Owner ยืนยันรับเงินตาม Payment Flow แล้ว ระบบจัดสรรและ Lock Slot ในขั้นนี้ และ Reservation พร้อมเข้าสู่ Auto Check-in
- `checked_in` — รถผ่าน Auto Check-in/Check-in และเข้าจอดแล้ว (Reservation ของ Walk-in ถูกสร้างในสถานะนี้ทันที)
- `completed` — Check-out เสร็จสิ้น
- `cancelled` — User หรือระบบยกเลิกก่อน Check-in
- `expired` — ไม่ Check-in ภายใน 1 ชั่วโมงหลังเวลาเริ่ม

### 7.4 การยกเลิก

- User สามารถยกเลิก Reservation ได้ทุกเวลาก่อน Check-in
- ไม่มีข้อกำหนดว่าต้องยกเลิกล่วงหน้ากี่นาที
- **ไม่คืน Deposit** เมื่อ User ยกเลิก (Deposit Payment ที่ชำระแล้วคงสถานะ `paid`)
- Deposit Payment ที่ยังไม่ได้ชำระ เปลี่ยนเป็น `void`
- Slot ที่ Lock ไว้ (ถ้ามี) ต้องถูกคืนเป็น `available` หลังยกเลิก

### 7.5 การลบ Reservation

- **ห้าม Hard Delete Reservation โดยตรง** ให้ใช้การยกเลิก (`cancelled`) แทน
- ข้อยกเว้น: เมื่อลบ Parking Lot หรือ User ข้อมูล Reservation ที่ผูกอยู่จะถูกลบตามไปด้วย

## 8. ระบบมัดจำ (Deposit)

### 8.1 การคำนวณ

Deposit ของ Reservation คำนวณจากอัตราค่าจอดของ Parking Lot ที่ถูกเลือก

```text
Deposit = hourly_rate × 1 ชั่วโมง
```

ตัวอย่าง:

```text
hourly_rate = 50 บาท/ชั่วโมง
Deposit = 50 บาท
```

```text
hourly_rate = 100 บาท/ชั่วโมง
Deposit = 100 บาท
```

### 8.2 การใช้งาน

สำหรับ User ที่จองล่วงหน้า:

```text
เลือก Lot + เวลา + ข้อมูลรถ
        ↓
คำนวณ Deposit
        ↓
ชำระ Deposit
        ↓
Admin/Owner ยืนยันรับเงิน (Mark as Paid)
        ↓
ยืนยัน Reservation
```

Deposit เป็นเงินที่ชำระเพื่อยืนยันการจอง ไม่ใช่ส่วนลด

การชำระ Deposit ใน Scope ปัจจุบันเป็นการจำลอง — User ไม่มีขั้นตอนชำระเงินในระบบ มีเพียงการรอ Admin/Owner กด `Mark as Paid`

### 8.3 กรณียกเลิก

- User ยกเลิกได้ก่อน Check-in
- Deposit **ไม่คืน**
- ถ้า Reservation ถูกยกเลิกหรือหมดอายุก่อนชำระ Deposit → Deposit Payment เป็น `void`

### 8.4 กรณี Walk-in

```text
Deposit = 0
```

Walk-in ไม่ต้องชำระ Deposit ไม่มี Deposit ให้นำไปหักในตอน Checkout และไม่มีส่วนลด `reservation_fee`

## 9. ระบบส่วนลด (`reservation_fee`)

`reservation_fee` ใช้เป็น **ส่วนลดเพียงรายการเดียวที่ระบบรองรับในขอบเขตปัจจุบัน**

ระบบไม่รวม:

- Promotion
- Coupon
- Discount Code

รายการเหล่านี้ถูกพักไว้และไม่ต้องนำมาเป็นส่วนหนึ่งของ Core Requirement ปัจจุบัน

`reservation_fee` เป็นส่วนลดที่นำไปคำนวณกับยอดค่าใช้บริการตาม Flow ของ Checkout

ข้อกำหนด:

```text
reservation_fee = hourly_rate ของลาน
```

- ใช้เฉพาะ Reservation ที่มีการชำระ Deposit
- **Walk-in ไม่มีส่วนลด `reservation_fee`** เพราะไม่ได้ชำระ Deposit
- `reservation_fee` และ Deposit เป็นคนละรายการ ห้ามใช้ฟิลด์เดียวกัน

## 10. ระบบ Auto Check-in

Auto Check-in เป็นหนึ่งใน Core Feature ของระบบ และต้องรองรับทั้ง Reservation และ Walk-in

### 10.1 Auto Check-in / Manual Check-in / Auto Check-out / Manual Check-out

ระบบรองรับทั้งกระบวนการอัตโนมัติและการดำเนินการโดยเจ้าหน้าที่ตามความเหมาะสมของสถานการณ์

**Check-in**

- **Auto Check-in เป็นกระบวนการหลัก** โดยรับภาพรถจาก Upload ที่ใช้จำลอง Camera Hardware แล้วให้ AI วิเคราะห์และจับคู่ Reservation
- **Manual Check-in ยังคงมีอยู่** เพื่อใช้เป็น Fallback เมื่อ Auto Check-in ไม่สามารถดำเนินการต่อได้ เช่น AI อ่านข้อมูลไม่ได้หรือผลตรวจไม่ผ่านเกณฑ์
- Manual Check-in ต้องใช้ข้อมูลรถและ Lot ตามข้อมูลของระบบ
- ผู้มีสิทธิ์ Manual Check-in: **Owner ของลานที่รถเข้า** หรือ **Admin เมื่อรถเข้าลานของ Admin** (`owner_id = NULL`)
- Manual Check-in ทำได้จากปุ่มเช็คอินของการจองที่ `confirmed` เท่านั้น — รับรถที่มาก่อนเวลาจองได้ (ระบบแจ้งเจ้าหน้าที่แล้ว) แต่ไม่รับการจองที่เลยเวลาเช็คอิน (§10.10)

**Check-out**

- **Auto Check-out** รองรับการรับภาพรถคันเดิมจาก Upload เพื่อจำลอง Camera Hardware ฝั่งทางออก และใช้ข้อมูลจากระบบในการระบุรถที่กำลังจะออก
- **Manual Check-out ยังคงมีอยู่** สำหรับกรณีที่ Auto Check-out ไม่สามารถดำเนินการได้
- ทั้ง Auto Check-out และ Manual Check-out ต้องเข้าสู่ Checkout Flow เดียวกันในการคำนวณค่าจอด สร้าง/อัปเดต Payment เปลี่ยนสถานะ Reservation/Parking Log และคืน Slot

### 10.2 ข้อจำกัดของต้นแบบ

ระบบจริงมีเป้าหมายให้ **กล้องจริง** เป็นแหล่งรับภาพรถและส่งภาพเข้าสู่ระบบโดยอัตโนมัติ

แต่ในโครงงานนี้:

> **Upload รูปภาพ = ตัวแทน Camera Input**

ดังนั้น Requirement ของต้นแบบคือผู้ใช้/ผู้ปฏิบัติงานอัปโหลดภาพรถเพื่อจำลองข้อมูลที่กล้องจริงจะส่งให้ระบบในอนาคต

การอัปโหลดภาพเป็นเพียงการจำลองกล้อง Hardware ของลาน จึงไม่ขึ้นกับตัวผู้อัปโหลด:

- ผู้ใช้ทุก Role สามารถอัปโหลดภาพเพื่อจำลองกล้องได้
- เลือกลาน (ตำแหน่งกล้อง) ได้ทุกลาน รวมถึงลานของ Owner รายอื่น โดยไม่ขึ้นกับสถานะเปิด/ปิดรับ Reservation
- ผลการสแกนผูกกับลานที่เลือก ไม่ผูกกับผู้อัปโหลด

### 10.2.1 Flow หลัก

```text
รถเข้ามา
   ↓
รับภาพรถ (Upload รูปแทนกล้องจริง)
   ↓
AI Vision วิเคราะห์ภาพ
   ↓
อ่านข้อมูล
- ทะเบียน
- จังหวัด
- ยี่ห้อ
- สี
- Accuracy
   ↓
ตรวจสอบ Accuracy
   ↓
ค้นหา Reservation ที่ตรงกัน
   ↓
ตรวจสอบ Parking Lot
   ↓
┌─────────────────────────────────┐
│ พบ Reservation และข้อมูลตรงกัน │
│ → Auto Check-in                 │
└─────────────────────────────────┘

┌─────────────────────────────────┐
│ ไม่พบ Reservation / ทะเบียนไม่ตรง │
│ → สร้าง Reservation แบบ Walk-in │
│ → Auto Check-in                 │
└─────────────────────────────────┘
```

### 10.3 เงื่อนไข Accuracy

- ระบบต้องใช้ค่า Accuracy จาก AI
- ผล AI ที่ Accuracy **ไม่เกิน 85%** ให้ถือว่าไม่ผ่านเกณฑ์
- เมื่อไม่ผ่านเกณฑ์ → ไม่ให้ Auto Check-in จากผลดังกล่าว และแจ้ง Owner + Admin
- Accuracy **มากกว่า 85%** จึงสามารถเข้าสู่กระบวนการ Matching ต่อได้

### 10.4 AI อ่านทะเบียนไม่ได้

กรณี AI ไม่สามารถอ่านทะเบียนได้:

- ไม่ให้ระบบจับคู่ Reservation จากทะเบียนนั้น
- แจ้งเตือนไปยัง Owner + Admin
- บันทึกเหตุการณ์การอ่านไม่สำเร็จ/ผล Scan ตามที่ระบบรองรับ

### 10.5 AI อ่านได้ แต่ไม่พบ Reservation

กรณี AI อ่านทะเบียนได้ แต่ค้นหา Reservation ที่ตรงกันไม่พบ:

- ไม่ถือเป็นข้อผิดพลาด
- ให้ถือเป็น **Walk-in**
- ระบบสร้าง Reservation ใหม่
- `user = Walkin User`
- `reserve_start = เวลาปัจจุบัน`
- `deposit = 0`
- ไม่มีส่วนลด `reservation_fee`
- จากนั้น Auto Check-in ต่อทันที และ Reservation มีสถานะ `checked_in`

### 10.6 กฎการจับคู่ Reservation

Reservation จะถือว่าตรงกับรถที่ AI อ่านได้ เมื่อ:

1. **ทะเบียนต้องตรง** โดยรวมทั้ง
    - หมายเลขทะเบียน
    - จังหวัด
2. และต้องมีอย่างน้อยหนึ่งรายการตรงกันระหว่าง
    - ยี่ห้อรถ
    - สีรถ

เขียนเป็น Logic ได้ดังนี้:

```text
ทะเบียน + จังหวัด ต้องตรง
AND
(ยี่ห้อตรง OR สีตรง)
```

### 10.7 กรณีทะเบียนไม่ตรง

ถ้าทะเบียน หรือ จังหวัด ไม่ตรงกับ Reservation:

> ถือว่า **ไม่พบ Reservation** และเข้าสู่ Walk-in Flow

ไม่ใช่การแจ้งว่า Reservation เดิมผิดแล้วหยุดกระบวนการ

### 10.8 ตรวจสอบ Parking Lot

เมื่อ AI/ระบบต้องค้นหา Reservation ต้องตรวจสอบด้วยว่า Reservation นั้นอยู่ใน Parking Lot ที่กำลังรับรถคันดังกล่าว

ไม่ควรนำ Reservation ของอีกลานหนึ่งมา Check-in เข้าอีกลานหนึ่งโดยอัตโนมัติ

### 10.9 Blacklist

ถ้ารถที่ AI ตรวจพบอยู่ในบัญชีดำ (ตรวจด้วยทะเบียน + จังหวัด):

- **ยังอนุญาตให้ Check-in**
- แจ้งเตือน Admin + Owner
- บันทึกเหตุการณ์ตามระบบ Log

Blacklist จึงเป็นระบบ **เฝ้าระวังและแจ้งเตือน** ไม่ใช่กฎ Block การเข้าจอดใน Requirement ปัจจุบัน

### 10.10 กรณีพิเศษของ Auto Check-in (ตัดสินใจ 2026-09-13)

ระบบค้นหาการจอง (`pending` / `confirmed`) ด้วย ทะเบียน + จังหวัด แล้วตัดสินตามลานที่กล้องติดตั้ง:

| กรณี                                                                  | ผลลัพธ์                                                                                         |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| AI อ่านเลขทะเบียนได้แต่อ่านจังหวัดไม่ได้                                  | ถือเป็น **อ่านทะเบียนไม่ได้** (§10.4)                                                             |
| การจอง `confirmed` ในลานนี้ + อยู่ในช่วงเช็คอิน + ยี่ห้อหรือสีตรง          | Auto Check-in ด้วยการจองเดิม                                                                    |
| การจอง `confirmed` ในลานนี้ แต่ **ยี่ห้อและสีไม่ตรงทั้งคู่**                  | ยัง Auto Check-in ด้วยการจองเดิม + แจ้ง Owner/Admin ของลานให้ตรวจสอบ                              |
| การจอง `confirmed` ในลานนี้ แต่ **มาก่อนเวลาจอง**                          | ไม่ Auto Check-in · แจ้ง Owner/Admin ของลาน ให้เจ้าหน้าที่ **Manual Check-in**                        |
| การจองอยู่ **ลานอื่น**                                                    | Check-in เป็น Walk-in ในลานนี้ + แจ้ง Owner/Admin ของลานนี้ (การจองเดิมยังคงอยู่)                     |
| การจองในลานนี้ยัง **`pending`** หรือ **เลยเวลาเช็คอิน**                     | Check-in เป็น Walk-in แยก + แจ้ง Owner/Admin ของลานนี้ (การจองเดิมยังคงอยู่)                         |
| ไม่พบการจอง / ทะเบียนหรือจังหวัดไม่ตรง                                   | Walk-in (§10.5, §10.7)                                                                          |
| รถคันนี้ยังจอดอยู่ (ยังไม่ Check-out)                                     | ไม่เช็คอินซ้ำ                                                                                     |

- Walk-in **ไม่ถูกนับ** ในกฎ 1 Active Reservation ต่อ ทะเบียน + จังหวัด (รถคันเดียวกันยังจอดได้ครั้งละ 1 รายการตาม Parking Log)
- **Manual Check-in** ใช้ได้กับการจองที่ `confirmed` เท่านั้น รับรถที่มาก่อนเวลาจองได้ แต่ไม่รับการจองที่เลยเวลาเช็คอินแล้ว

## 11. ระบบ Walk-in

Walk-in ต้องใช้ Flow เดียวกับ Reservation ปกติให้มากที่สุด

### 11.1 หลักการ

```text
รถเข้ามา
↓
AI Scan
↓
ไม่พบ Reservation
↓
สร้าง Reservation อัตโนมัติ
↓
User = Walkin User
↓
reserve_start = เวลาปัจจุบัน
↓
Deposit = 0
↓
ระบบเลือก Slot อัตโนมัติ
↓
Auto Check-in
```

### 11.2 ข้อมูล Walk-in

Walk-in ใช้ข้อมูลรถชุดเดียวกับ Reservation:

- ทะเบียน
- จังหวัด
- ยี่ห้อ
- สี

### 11.3 Checkout ของ Walk-in

- ไม่มี Deposit
- ไม่ต้องหัก Deposit ตอน Checkout
- ค่าจอดคำนวณจากระยะเวลาจอดจริงและ `hourly_rate`
- **ไม่มีส่วนลด `reservation_fee`** เนื่องจาก Walk-in ไม่ได้ชำระ Deposit
- ยอดสุทธิ = ค่าจอดจริง

### 11.4 ลานที่ Walk-in เข้าได้

- Walk-in เข้าได้ทุกลานที่มี Slot ว่าง โดยไม่ต้องมี Reservation ล่วงหน้า และไม่ขึ้นกับสถานะเปิด/ปิดรับ Reservation
- ระบบต้องแสดงว่าจัด Slot ใดให้รถคันนั้น
- `Walkin User` ไม่ได้รับ Notification

### 11.5 กรณีลานเต็ม

ถ้ารถ Walk-in เข้ามาในลานที่ไม่มี Slot ว่าง:

- แสดงข้อความว่า **ลานเต็ม**
- **ไม่บันทึกข้อมูลอื่นใด** — ไม่สร้าง Reservation, Parking Log, Payment และไม่บันทึกผล Scan
- ยกเว้นการตรวจทะเบียน + จังหวัดกับ Blacklist — ถ้าพบ ให้แจ้ง Admin + Owner และบันทึกเหตุการณ์ Blacklist ใน Log

## 12. ระบบ Check-out และการคำนวณค่าจอด

### 12.1 เวลาในการคิดค่าจอด

เวลาจอดจริงคำนวณจาก:

```text
Check-out Time - Check-in Time
```

และนำระยะเวลาไปคิดตามกติกาค่าจอดของลาน

### 12.2 อัตราค่าจอด

ใช้ `hourly_rate` ของ Parking Lot ที่เกี่ยวข้องกับรายการจอด

ระบบต้องรักษาข้อมูลอัตราที่ใช้กับรายการจอดตามความเหมาะสม เพื่อไม่ให้การแก้ `hourly_rate` ในภายหลังทำให้ประวัติเดิมเปลี่ยนโดยไม่ตั้งใจ

### 12.3 การหัก Deposit

กรณี Reservation ที่ชำระ Deposit มาแล้ว:

```text
ค่าจอดจริง
− Deposit
− reservation_fee
= ยอดสุทธิที่ต้องชำระ
```

โดยยอดสุทธิต้องไม่ติดลบ

กรณี Walk-in (ไม่หัก Deposit และไม่หัก `reservation_fee`):

```text
ค่าจอดจริง
= ยอดสุทธิที่ต้องชำระ
```

### 12.4 หลัง Check-out

เมื่อ Check-out สำเร็จ:

- บันทึก `check_out_time`
- คำนวณยอดเงิน
- สร้าง/ปรับปรุง Payment ตาม Flow
- เปลี่ยน Reservation เป็น `completed`
- เปลี่ยน Slot เป็น `available`
- บันทึก Parking Log
- ส่ง Notification ตามสิทธิ์

### 12.5 รายละเอียดที่กำหนดเพิ่ม (2026-09-14)

- **Auto Check-out:** ระบบตรวจทิศทางเองจากผลสแกน — ถ้ารถ (ทะเบียน + จังหวัด) กำลังจอดอยู่ในลานที่สแกน → Check-out อัตโนมัติ · ถ้าไม่ได้จอดอยู่ → เข้าสู่ Auto Check-in / Walk-in
- สแกนแล้ว Check-out อัตโนมัติไม่ได้ (AI ไม่ผ่านเกณฑ์ / อ่านทะเบียนหรือจังหวัดไม่ได้ / รถจอดอยู่ลานอื่น) → บันทึกผลสแกน + แจ้ง Owner/Admin ของลานที่สแกน ให้ใช้ Manual Check-out
- **Manual Check-out:** ปุ่มเช็คเอาท์ของรายการที่ `checked_in` โดย Owner ของลาน หรือ Admin สำหรับลานของ Admin — ใช้ Checkout Flow เดียวกับ Auto
- **ค่าจอด:** ปัดขึ้นรายชั่วโมง ขั้นต่ำ 1 ชั่วโมง (นับจากนาทีเต็ม) × `hourly_rate` **ณ ตอน Check-in** ซึ่งบันทึกไว้ใน Parking Log
- **การหัก:** หัก Deposit Payment ที่ `paid` ก่อน แล้วจึงหัก `reservation_fee` — แต่ละรายการหักได้ไม่เกินยอดที่เหลือ ยอดสุทธิไม่ติดลบ
- ยอดสุทธิ = 0 → Checkout Payment เป็น `paid` โดยระบบ (`paid_by` ว่าง) · มากกว่า 0 → `unpaid` รอ Admin/Owner Mark as Paid

## 13. ระบบ Payment

ระบบต้องรองรับ Payment อย่างน้อย 2 ประเภท:

1. **Deposit Payment** — เกิดตอนสร้าง Reservation และใช้เป็นเงื่อนไขสำหรับยืนยันการจอง
2. **Checkout Payment** — เกิดหลัง Check-out สำหรับยอดคงเหลือที่ต้องชำระ

### 13.1 การยืนยันรับเงิน (Mark as Paid)

โครงงานนี้ใช้การยืนยันรับเงินโดยเจ้าหน้าที่เป็นหลักแทนระบบตรวจสลิปหรือ Payment Gateway

ผู้ที่มีสิทธิ์ยืนยันรับเงิน:

- Admin
- Owner ตามขอบเขต Parking Lot ของตนเอง

การกด `Mark as Paid` หมายถึง:

> เจ้าหน้าที่ตรวจสอบและยืนยันด้วยตนเองว่าได้รับเงินของรายการนั้นแล้ว

### 13.2 Reservation Deposit Payment

Flow:

```text
สร้าง Reservation
   ↓
คำนวณ Deposit = hourly_rate × 1
   ↓
สร้างรายการ Deposit Payment
   ↓
รอการชำระ
   ↓
Admin/Owner ตรวจสอบและกด Mark as Paid
   ↓
Reservation = confirmed
```

ต้องป้องกันการยืนยันรับเงินซ้ำ และต้องตรวจสอบได้ว่าใครเป็นผู้กด Mark as Paid และกดเมื่อใด

หาก Reservation ถูกยกเลิกหรือหมดอายุก่อน Deposit ได้รับการยืนยันรับเงิน ให้เปลี่ยน Deposit Payment เป็น `void` และห้าม Mark as Paid รายการที่เป็น `void`

หากขณะกด Mark as Paid ลานไม่มี Slot ว่างให้ Lock:

- ไม่ยืนยัน Reservation
- Reservation เปลี่ยนเป็น `cancelled`
- Deposit Payment เปลี่ยนเป็น `void` เนื่องจากยังไม่ได้ยืนยันรับเงิน
- แจ้งเตือน User เจ้าของ Reservation

### 13.3 Checkout Payment

หลัง Check-out ระบบต้องแสดง:

- ค่าจอดจริง
- Deposit ที่ชำระแล้ว (ถ้ามี)
- `reservation_fee` ที่เป็นส่วนลด (ถ้ามี)
- ยอดสุทธิ
- สถานะการชำระ

หากมียอดคงเหลือ:

```text
ยอดสุทธิ
  ↓
รอการรับชำระ
  ↓
Admin/Owner ตรวจสอบและ Mark as Paid
```

หากไม่มียอดคงเหลือ ระบบต้องบันทึกผลการชำระตามกติกาของระบบโดยไม่สร้างหนี้ค้างเกินจริง

### 13.4 Walk-in Payment

Walk-in มี Deposit = 0 และไม่มี Deposit Payment

เมื่อ Check-out:

- ไม่หัก Deposit
- คำนวณค่าจอดจริงตาม `hourly_rate`
- ไม่หัก `reservation_fee`
- หากมียอดคงเหลือ ให้ใช้การยืนยันรับเงินโดย Admin/Owner

### 13.5 Payment Gateway / Slip Verification

ยังไม่อยู่ใน Scope ปัจจุบัน:

- QR Payment
- Payment Gateway ภายนอก
- Slip Upload / OCR Slip Verification
- Automatic bank transfer verification

ยังถือเป็นเรื่องที่สามารถพิจารณาในอนาคตได้ แต่ห้ามนำมาเป็นเงื่อนไขบังคับของ Core System ปัจจุบัน

## 14. ระบบบัญชีดำ (Blacklist / Suspicious Vehicles)

Admin สามารถจัดการรายการรถต้องสงสัยได้

ข้อมูลที่ควรรองรับ:

- เลขทะเบียน
- จังหวัด
- เหตุผล
- ระดับความเสี่ยง เช่น `low`, `medium`, `high`
- สถานะเปิด/ปิดรายการ

### 14.1 การตรวจสอบ

เมื่อ AI Scan ตรวจพบรถ:

1. เปรียบเทียบทะเบียน + จังหวัด กับ Blacklist
2. ถ้าพบ → แจ้ง Admin + Owner
3. **ไม่ Block Check-in** ตาม Requirement ปัจจุบัน
4. บันทึกเหตุการณ์ในระบบ Log

### 14.2 การจัดการรายการ

Admin สามารถ:

- เพิ่ม
- แก้ไข
- ลบ
- ค้นหา
- เปิด/ปิดรายการ
- ตรวจสอบประวัติที่เกี่ยวข้องตามข้อมูลที่ระบบบันทึก

## 15. ระบบ Notification

ระบบต้องมี Notification ภายในเว็บ และมีสถานะอย่างน้อย:

- ยังไม่อ่าน (`unread`)
- อ่านแล้ว (`read`)

### 15.1 Notification ของ User

เหตุการณ์สำคัญ เช่น:

- Reservation ยืนยัน
- Reservation ถูกยกเลิก (รวมกรณีลานเต็มขณะยืนยันรับเงิน Deposit)
- Reservation Expired
- Auto Check-in สำเร็จ
- Check-out สำเร็จ
- Payment/ยอดเงินที่เกี่ยวข้อง

`Walkin User` ไม่ได้รับ Notification

### 15.2 Notification ของ Owner

เหตุการณ์สำคัญ เช่น:

- AI อ่านทะเบียนไม่ได้
- AI Accuracy ไม่ผ่านเกณฑ์
- พบรถ Blacklist
- เหตุการณ์สำคัญของลาน

> รายการผู้รับที่ใช้จริงอยู่ใน §15.4 (ตัดสินใจ 2026-09-14) — การจองใหม่ **ไม่แจ้ง** ผู้ดูแลลาน

### 15.3 Notification ของ Admin

เหตุการณ์สำคัญ เช่น:

- AI อ่านทะเบียนไม่ได้
- AI Accuracy ไม่ผ่านเกณฑ์
- พบรถ Blacklist
- Owner Application ใหม่
- คำร้องลาออกของ Owner
- เหตุการณ์ผิดปกติที่ระบบต้องการให้ตรวจสอบ

### 15.4 รายละเอียดที่กำหนดเพิ่ม (2026-09-14)

**ผู้ดูแลลาน** = Owner ของลาน · ลานของ Admin (`owner_id = NULL`) = Admin ทุกคน

แจ้งเจ้าหน้าที่เฉพาะเหตุการณ์ "รถต้องสงสัย" และ "Auto Check-in / Check-out ไม่ผ่าน":

| เหตุการณ์                                      | ผู้รับ                          |
| ---------------------------------------------- | ------------------------------- |
| AI อ่านทะเบียน/จังหวัดไม่ได้                      | Owner ของลาน + Admin ทุกคน       |
| AI Accuracy ไม่เกิน 85%                         | Owner ของลาน + Admin ทุกคน       |
| พบรถ Blacklist (รวมกรณีลานเต็ม)                 | Owner ของลาน + Admin ทุกคน       |
| รถมาก่อนเวลาจอง (รอ Manual Check-in)             | ผู้ดูแลลาน                        |
| ยี่ห้อ/สีไม่ตรงแต่เช็คอินแล้ว                      | ผู้ดูแลลาน                        |
| Auto Check-out ไม่สำเร็จ                         | ผู้ดูแลลาน                        |
| Owner Application ใหม่/ส่งใหม่ · Owner ลาออก     | Admin ทุกคน                     |

- **ไม่แจ้ง** ผู้ดูแลลานเมื่อ: มีการจองใหม่ (แทนที่ "มี Reservation ในลาน" ใน §15.2), User ยกเลิก, การจองหมดอายุ, ยอดค่าจอดค้างชำระ, รถเข้าเป็น Walk-in เพราะใช้การจองไม่ได้, รถที่จอดอยู่ลานอื่นผ่านกล้อง — เหตุการณ์เหล่านี้ยังบันทึกใน Audit Log
- **User** ได้รับ: การจองยืนยัน, การจองถูกยกเลิก (รวมลานเต็มขณะยืนยันรับเงิน), ยกเลิกเอง, หมดอายุ, เช็คอิน (อัตโนมัติ/โดยเจ้าหน้าที่), เช็คเอาท์พร้อมยอดเงิน, ผลคำขอเป็น Owner — ไม่มีการแจ้งเพิ่มเติม
- บัญชีระบบ (`Walkin User`) ไม่ได้รับ Notification ทุกกรณี

## 16. Owner Application

ระบบต้องรองรับการสมัครเป็น Owner เพื่อให้ระบบเป็น Multi-owner

### ขั้นตอน

```text
User
↓
ส่ง Owner Application
↓
กรอกข้อมูลธุรกิจ/ลาน/ข้อมูลติดต่อ/เอกสาร
↓
Admin ตรวจสอบ
↓
อนุมัติ → Owner
หรือ
ปฏิเสธ → User พร้อมเหตุผล
```

กรณี Owner ต้องการลาออก:

```text
Owner
↓
ส่งคำร้องลาออก
↓
Admin ตรวจสอบและอนุมัติ
↓
ยกเลิก Reservation ที่ยังไม่ Check-in (pending / confirmed) ในลานของ Owner
↓
รถที่อยู่ในสถานะ checked_in → ระบบ Check-out
↓
แจ้งผู้ได้รับผลกระทบให้ติดต่อ Admin
↓
ลบลานของ Owner (ข้อมูลที่ผูกกับลานถูกลบตามไปด้วย)
↓
Owner กลับเป็น User
```

- การลาออก **ต้องได้รับการอนุมัติจาก Admin ก่อน** จึงจะมีผล
- ระหว่างรอการอนุมัติ Owner ยังคงเป็น Owner
- Payment และประวัติทั้งหมดของลานที่ถูกลบ (รวม Checkout Payment ที่เกิดจากขั้นตอนนี้) จะถูกลบตามไปด้วย

### 16.1 รายละเอียดที่กำหนดเพิ่ม (2026-09-14)

- **คำร้องลาออก** เก็บในตาราง `owner_resignations` (`pending` / `approved` / `rejected`) แยกจาก Owner Application — Owner มีคำร้องที่รอพิจารณาได้ครั้งละ 1 รายการ; Admin พิจารณาที่หน้า `คำร้องลาออก Owner` (แสดงผลกระทบ: จำนวนลาน / การจองที่จะถูกยกเลิก / รถที่จะถูกเช็คเอาท์)
- **อนุมัติ:** ยกเลิกการจอง `pending`/`confirmed` (มัดจำที่ยังไม่ชำระ → `void`) → ระบบ Check-out รถ `checked_in` → แจ้งผู้จองว่าลานยุติการให้บริการ กรุณาติดต่อ Admin (แทนข้อความมาตรฐาน) → ลบลาน → Owner กลับเป็น User → แจ้ง Owner; บันทึกสรุปผลในคำร้องและ Audit Log
- **ไม่อนุมัติ:** Admin ต้องระบุเหตุผล (อย่างน้อย 10 ตัวอักษร) → แจ้ง Owner พร้อมเหตุผล; Owner ยื่นคำร้องใหม่ได้
- **ลบลาน (Owner):** ลบไม่ได้ถ้ายังมีการจอง `pending` / `confirmed` / `checked_in`
- **รายได้ของ Owner** = เงินที่รับจริง: มัดจำที่ `paid` + ยอดค่าจอดหลัง Check-out ที่ `paid` (ยอดสุทธิหลังหักมัดจำ จึงไม่นับซ้ำ) นับตามเวลาที่ยืนยันรับเงิน (`paid_at`) — ใช้ทั้ง Owner Dashboard และหน้า Revenue; "ค้างชำระ" = ค่าจอดหลัง Check-out ที่ยัง `unpaid`

## 17. ระบบ Dashboard และรายงาน

### 17.1 Admin Dashboard

ควรแสดงข้อมูลระดับระบบ เช่น:

- รถที่กำลังจอด

- สถิติ AI Scan
- สถิติ Blacklist/เหตุการณ์สำคัญตามความเหมาะสม

### 17.2 Owner Dashboard

ควรแสดงเฉพาะข้อมูลของลานที่ Owner เป็นเจ้าของ เช่น:

- Slot ว่าง
- รถที่จอด
- Reservation
- รายได้
- สถิติรายวัน/รายเดือน

### 17.3 User Dashboard

ควรแสดง:

- Reservation ปัจจุบัน
- สถานะการจอง
- รายการจอดปัจจุบัน
- ประวัติการจอด

Notification ไม่ได้อยู่บนหน้า Dashboard แต่เข้าถึงได้จากทุกหน้าผ่านกระดิ่งบนแถบบน (มีตัวเลขจำนวนที่ยังไม่ได้อ่าน)
แท็บ "แจ้งเตือน" บนแถบล่างของมือถือ และหน้า `/notifications` — ตัดสินใจ 2026-09-20 ตอน UI Rebuild

### 17.4 Reports

ระบบควรรองรับรายงานที่จำเป็น เช่น:

- Reservation History
- Parking History
- Payment History
- Revenue Report
- Reservation Log
- Audit Log

### 17.5 CSV Export

CSV Export ให้ใช้งานเฉพาะ **Admin**

- Admin สามารถเลือกประเภทข้อมูลที่ต้องการ Export
- Admin สามารถใช้ตัวกรองของข้อมูลก่อน Export ตามที่แต่ละหน้ารองรับ
- ข้อมูลที่ Export ต้องสอดคล้องกับขอบเขตสิทธิ์ของ Admin
- Owner ไม่มีปุ่มหรือฟังก์ชัน CSV Export ในระบบ
- รูปแบบ CSV ต้องสามารถนำไปเปิดหรือประมวลผลต่อได้ และข้อมูลต้องไม่หลุดขอบเขตสิทธิ์

#### 17.5.1 รายละเอียดที่กำหนดเพิ่ม (2026-09-15)

- **ประเภทข้อมูลที่ Export ได้:** ประวัติการจอง (Reservation), ประวัติการจอด (Parking Log), รายงานรายได้รายวัน (Revenue), Reservation Log และ Audit Log — ไม่มี Export Payment แยก
- **ขอบเขต:** ทั้งระบบ ทุกลาน (ลานของ Admin และของ Owner) โดยเลือกกรองลานได้ — Audit Log ครอบคลุมทุก Role
- **หน้าจอ:** มีทั้งหน้า Export กลาง (เลือกประเภทข้อมูล + ตัวกรอง) และปุ่ม Export CSV ในหน้าการจอง / ประวัติการจอด / Reservation Log / Audit Log ซึ่งใช้ตัวกรองของหน้านั้น (ไฟล์ครอบคลุมทุกลาน)
- **ตัวกรอง:** การจอง = คำค้น, ลาน, สถานะ, ช่วงวันเริ่มจอง · ประวัติการจอด = ทะเบียน, ลาน, กำลังจอด/เช็คเอาท์แล้ว, ช่วงวันเข้า · รายได้ = ลาน, ช่วงวันที่ยืนยันรับเงิน (ไม่ระบุ = เดือนปัจจุบัน)
- **รายงานรายได้:** 1 แถว = 1 วัน × 1 ลาน — มัดจำ, ค่าจอด, รวม, จำนวนรายการ ตามนิยาม "เงินที่รับจริง" (§16.1)
- **รูปแบบไฟล์:** UTF-8 พร้อม BOM (เปิดภาษาไทยใน Excel ได้) และค่าที่ขึ้นต้นด้วย `=` `+` `-` `@` ถูกเติม `'` นำหน้าเพื่อกัน CSV/Formula Injection

## 18. Audit Log และการตรวจสอบย้อนหลัง

ระบบต้องบันทึกเหตุการณ์สำคัญของผู้ใช้และผู้ดูแลตามขอบเขตที่เหมาะสม เช่น:

- การจัดการ User
- การเปลี่ยน Role
- การอนุมัติ/ปฏิเสธ Owner Application
- การจัดการ Parking Lot/Slot
- การจัดการ Reservation
- Check-in / Check-out
- Payment
- Blacklist
- AI Scan ที่มีความผิดปกติหรือเกี่ยวข้องกับการแจ้งเตือน

Audit Log ต้องบันทึกการกระทำของ **ผู้ใช้งานทุก Role** ที่ระบบสามารถระบุผู้กระทำได้ ไม่ใช่เฉพาะ Admin รวมถึงเหตุการณ์ที่ระบบเป็นผู้ดำเนินการ (System) เช่น Auto Check-in, Walk-in และ Expire

Audit Log ควรเก็บข้อมูลอย่างน้อย:

- ผู้กระทำ (`actor`)
- Role ของผู้กระทำขณะทำรายการ
- Action
- Target/ข้อมูลที่เกี่ยวข้อง
- วันและเวลา
- รายละเอียดหรือ Metadata ที่จำเป็น

ตัวอย่าง Action ที่ควรบันทึก:

- Login/Logout และเหตุการณ์ Authentication สำคัญ
- สร้าง/แก้ไข/ยกเลิก Reservation
- Deposit Payment และ Mark as Paid
- Check-in / Check-out ที่เกิดจากระบบ
- จัดการ Parking Lot/Slot
- AI Scan และเหตุการณ์ AI ผิดปกติ
- Blacklist
- Owner Application และคำร้องลาออก
- เปลี่ยน Role
- จัดการข้อมูลที่มีผลต่อระบบ

### 18.1 รายละเอียดที่กำหนดเพิ่ม (2026-09-14)

- Audit Log เก็บในตาราง `admin_actions` ครอบคลุม Role `user` / `owner` / `admin` และ `system` (ระบบ = ไม่มีผู้กระทำ, ไม่เก็บ IP)
- **Payment Log** เก็บใน Audit Log: `payment.deposit_created`, `payment.mark_paid`, `payment.void`, `payment.checkout_created`
- **Authentication:** `auth.register`, `auth.login`, `auth.logout`, `auth.email_verified`, `auth.password_change`, `auth.password_reset` — ไม่บันทึก Login ที่ไม่สำเร็จ
- **Reservation:** `reservation.create`, `reservation.update_vehicle`, `reservation.confirm`, `reservation.cancel`, `reservation.check_in` (auto/manual), `reservation.walk_in`, `reservation.expire`, `reservation.check_out` (auto/manual)
- **AI Scan ที่ผิดปกติ (ระบบ):** `ai_scan.low_accuracy`, `ai_scan.unreadable`, `ai_scan.blacklist_detected`, `ai_scan.early_arrival`, `ai_scan.vehicle_mismatch`, `ai_scan.booking_not_used`, `ai_scan.parked_elsewhere`, `ai_scan.check_out_failed`
- **การจัดการ:** `parking_lot.*`, `parking_slot.*`, `user.*` (รวม `user.demote_owner`), `suspicious_vehicle.*`, `owner_application.*`, `owner_resignation.submit` / `approve` / `reject`, `profile.update`, `profile.delete` — ไม่บันทึกการเปิดดูหน้า
- **Admin** ดู Audit Log และ Reservation Log **ทั้งระบบ** (ทุกลาน ทุก Role รวมรายการของระบบ) พร้อมตัวกรองและ CSV Export
- **Owner** ดู Reservation Log เฉพาะลานของตนเอง — ไม่เห็น Audit Log และไม่มี CSV Export
- Log เฉพาะประเภทที่มีอยู่: Reservation Log (`reservation_logs`), Parking Log (`parking_logs`), AI Log (`license_plate_scans`), Notification (`notifications`)

## 19. Authentication และความปลอดภัย

ระบบต้องมีแนวทางควบคุมสิทธิ์อย่างชัดเจน

### 19.1 Authentication

- Register
- Login
- Logout
- Password Reset ตามความสามารถของระบบ
- Change Password
- Force Password Reset โดย Admin

### 19.2 Authorization

- User เข้าถึงเฉพาะข้อมูลของตนเอง
- Owner เข้าถึงเฉพาะข้อมูลของ Parking Lot ที่ตนเองเป็นเจ้าของ
- Admin มีสิทธิ์ System Administration แต่ Lot Ownership ต้องยังคงแยกจาก Owner
- Route ของ Role อื่นต้องไม่สามารถถูกเรียกใช้โดยไม่ได้รับอนุญาต
- Force Password Reset ต้องครอบคลุมผู้ใช้ทุก Role รวมถึง Admin ตามกฎของระบบ

### 19.3 Security Requirement สำคัญ

- ป้องกันการเข้าถึงข้อมูลข้าม Role
- ป้องกันการเข้าถึง Parking Lot ของ Owner รายอื่นโดยไม่ได้รับอนุญาต
- ป้องกันการจอง Slot ซ้ำจาก Concurrent Request
- Validation ข้อมูล Reservation และ AI Input
- ป้องกันการเข้าถึงไฟล์/เอกสารที่ไม่ควรเปิดสาธารณะ
- ไม่เก็บ Secret/Password สำคัญไว้ใน Source Code
- ใช้การยืนยัน SSL/TLS ที่เหมาะสมใน Environment ที่ใช้งานจริง
- จำกัดจำนวนครั้งการอัปโหลดภาพเข้า AI Scan เพื่อคุมค่าใช้จ่าย API และกันการใช้งานผิดปกติ (2026-09-20: `POST */scan` = 30 ครั้ง/นาที ต่อผู้ใช้ ทุก Role · เกินแล้วได้ HTTP 429)
- ใช้บัญชีฐานข้อมูลเฉพาะของโปรเจกต์ (ไม่ใช่ superuser) และไม่เก็บรหัสผ่านไว้ในไฟล์ที่ commit

### 19.4 รายละเอียดที่กำหนดเพิ่ม (2026-09-14)

- ต้องยืนยัน Email ก่อนใช้งานระบบหลัก (Dashboard, การจอง, สแกน, แจ้งเตือน, Owner/Admin Portal) — ก่อนยืนยันใช้ได้เฉพาะหน้า Profile, เปลี่ยนรหัสผ่าน, ยืนยันอีเมล และ Logout
- Force Password Reset ครอบคลุมทุก Role รวม Admin — ระหว่างนั้นใช้ได้เฉพาะหน้า Profile, เปลี่ยนรหัสผ่าน และ Logout
- ควบคุมสิทธิ์ตาม Role ด้วย Middleware `role:user` / `role:owner` / `role:admin` ตัวเดียว (+ `owner.approved` สำหรับเครื่องมือจัดการของ Owner) — ไม่มี Role/Permission Model แยก
- บัญชีระบบ (`Walkin User`) Login ไม่ได้ ขอรีเซ็ตรหัสผ่านไม่ได้ และถ้ามี Session ค้างอยู่จะถูกออกจากระบบทันที
- Ownership: Owner เข้าถึงเฉพาะลาน/ช่อง/การจอง/Payment/Log ของลานตนเอง · Admin จัดการเฉพาะลานของ Admin · User เข้าถึงเฉพาะการจอง/ประวัติ/แจ้งเตือนของตนเอง

## 20. โครงสร้างสถานะหลักของระบบ

### Reservation

```text
pending
  ↓
confirmed
  ↓
checked_in
  ↓
completed
```

หรือออกจาก Flow ก่อนหน้า:

```text
pending / confirmed
    ├── cancelled
    └── expired
```

### Parking Slot

```text
available
   ↓
reserved
   ↓
occupied
   ↓
available
```

กรณี Reservation ถูกยกเลิกหรือ Expire:

```text
reserved → available
```

### Payment

อย่างน้อยต้องสามารถแยกได้ว่า:

```text
unpaid / paid / void
```

- `unpaid` — รอการรับชำระ
- `paid` — Admin/Owner ยืนยันรับเงินแล้ว
- `void` — รายการถูกยกเลิกโดยไม่มีการรับเงิน เช่น Deposit ของ Reservation ที่ถูกยกเลิกหรือหมดอายุก่อนชำระ

โดยรายละเอียดสถานะเพิ่มเติมสามารถกำหนดตาม Implementation โดยไม่เปลี่ยน Business Rule หลักของ Deposit และ Checkout

## 23. ระบบ Expire Reservation อัตโนมัติ

ระบบต้องมีกระบวนการตรวจสอบ Reservation ที่เลยกำหนดเวลา Check-in

### กฎ

```text
reserve_start + 1 ชั่วโมง
```

ถ้ายังไม่ Check-in:

1. เปลี่ยน Reservation เป็น `expired`
2. คืน Slot ที่ Lock ไว้ (ถ้ามี) ให้ `available`
3. ป้องกันไม่ให้ Reservation หมดอายุยังสามารถถูก Check-in ได้
4. ส่ง Notification ให้ User ตามความเหมาะสม
5. บันทึก Log/เหตุการณ์ที่เกี่ยวข้อง
6. Deposit Payment ที่ยังไม่ได้ชำระเปลี่ยนเป็น `void`

การทำงานนี้สามารถใช้ Laravel Scheduler ตรวจสอบเป็นระยะ เช่น ทุก 1 นาที

### รายละเอียดที่กำหนดเพิ่ม (2026-09-14)

- ครบ 60 นาทีพอดียังอยู่ในช่วง Check-in · Expire เมื่อ **เกิน** 60 นาที (Scheduler ทำงานทุก 1 นาที)
- ใช้กับ Reservation สถานะ `pending` และ `confirmed` เท่านั้น
- Deposit ที่ชำระแล้วไม่คืน (คงสถานะ `paid`) · Deposit ที่ยังไม่ชำระเปลี่ยนเป็น `void`
- ถ้า Admin/Owner กด Mark as Paid หลังเลยช่วง Check-in แล้วแต่ Scheduler ยังไม่ทำงาน → ระบบ Expire การจองแทนการยืนยัน และ Deposit เป็น `void`
- ระยะเวลา 1 ชั่วโมงเป็น Business Rule คงที่ ไม่ปรับผ่าน `.env`

## 24. การป้องกันการจอง Slot ซ้ำ

ในกรณีที่ User หลายคนส่ง Reservation ในเวลาใกล้เคียงกัน ระบบต้องไม่สามารถจัด Slot เดียวกันให้มากกว่าหนึ่ง Reservation ได้

แนวทางหลัก:

- ใช้ Database Transaction
- ใช้ Row Lock / `lockForUpdate` หรือกลไกที่เหมาะสม
- ตรวจสถานะ Slot อีกครั้งภายใน Transaction
- อัปเดต Reservation และ Slot ให้เป็น Atomic Operation เท่าที่ทำได้

```text

   ↓

   ↓
สร้าง Deposit Payment (unpaid)
   ↓
ชำระ Deposit (จำลอง)
   ↓
Admin/Owner Mark as Paid
   ↓
Reservation Confirmed
   ↓
ระบบจัดสรรและ Lock Slot
   ↓
รอรถเข้ามา
   ↓
Auto Check-in
   ↓
Slot = Occupied
   ↓
จอดรถ
   ↓
Check-out
   ↓
คำนวณค่าจอดจริง
   ↓
หัก Deposit + reservation_fee
   ↓
Payment
   ↓
Reservation Completed
   ↓
Slot = Available
```

### 28.2 Walk-in Flow

```text
รถเข้ามา
   ↓
รับภาพรถ (Upload แทนกล้องจริง)
   ↓
AI อ่านข้อมูล
   ↓
Accuracy > 85%
   ↓
ค้นหา Reservation
   ↓
ไม่พบ / ทะเบียนไม่ตรง
   ↓
ตรวจ Slot ว่าง
   ├── ลานเต็ม → แสดง "ลานเต็ม" + ตรวจ Blacklist (พบ → แจ้ง Admin/Owner + บันทึก Blacklist Event) → จบ
   ↓
สร้าง Reservation แบบ Walk-in
   ↓
Walkin User
   ↓
Reserve Start = เวลาปัจจุบัน
   ↓
Deposit = 0
   ↓
ระบบจัด Slot อัตโนมัติ
   ↓
Auto Check-in (status = checked_in)
   ↓
Slot = Occupied
   ↓
Check-out
   ↓
คำนวณค่าจอดจริง
   ↓
ไม่หัก Deposit
   ↓
ไม่หัก reservation_fee
   ↓
Payment
   ↓
Completed
```

### 28.3 Admin และ Reservation

Admin **ไม่สามารถสร้าง Reservation แบบ Manual** — Reservation ในระบบเกิดจาก 2 ทางเท่านั้น:

1. User สร้างผ่าน Reservation Flow (§28.1)
2. ระบบสร้างผ่าน Walk-in Flow (§28.2)

บทบาทของ Admin ต่อ Reservation คือ ดู ค้นหา ตรวจสอบประวัติ ยกเลิก/จัดการเหตุผิดปกติ และยืนยันรับเงิน Deposit (`Mark as Paid`) ตามสิทธิ์

### 28.4 AI Error Flow

```text
รับภาพ
 ↓
AI Scan
 ├── Accuracy <= 85%
 │      → แจ้ง Owner + Admin
 │      → ไม่ผ่าน Auto Check-in จากผลนั้น
 │
 └── อ่านทะเบียนไม่ได้
        → แจ้ง Owner + Admin
        → ไม่สามารถ Matching จากทะเบียนได้
```

### 28.5 Blacklist Flow

```text
AI Scan
   ↓
ตรวจสอบ Blacklist
   ↓
พบ Blacklist
   ├── Check-in ได้
   └── แจ้ง Admin + Owner
```

## 29. ผลลัพธ์ที่คาดหวัง

เมื่อระบบเสร็จสมบูรณ์ คาดว่าจะสามารถ:

1. ให้ผู้ใช้จองลานจอดล่วงหน้าและชำระ Deposit เพื่อยืนยันการจองได้
2. จัดการ Slot อัตโนมัติโดยไม่ให้ User เลือกช่องเอง
3. บังคับยืนยัน Email ก่อนใช้งานระบบหลัก
4. รองรับ Auto Check-in ทั้ง Reservation และ Walk-in ด้วย Flow เดียวกัน
5. ใช้ AI วิเคราะห์ข้อมูลรถจากภาพจริงที่จำลองด้วย Upload รูปในโครงงาน
6. ลดการกรอกข้อมูลรถด้วยมือและเพิ่มความรวดเร็วในการ Check-in
7. ตรวจจับรถ Blacklist และแจ้งเตือนผู้ดูแลที่เกี่ยวข้อง
8. คำนวณค่าจอดและยอดชำระหลัง Check-out ได้อัตโนมัติ
9. ให้ Owner ติดตามสถานะลาน รายได้ และข้อมูลการจอดได้
10. ให้ Admin บริหารจัดการระบบ ผู้ใช้ Owner Application Logs และบริการระดับระบบได้
11. รองรับการขยายต่อไปสู่ Camera Input จริง และ Marketplace ที่ใช้ GPS

## 30. หลักการพัฒนาต่อจากเอกสารนี้

เอกสารฉบับนี้เป็น **Business Requirement / Project Plan** สำหรับกำหนดพฤติกรรมของระบบ ไม่ใช่รายละเอียด Implementation ของโค้ดทุกบรรทัด

การพัฒนาต่อควรยึดหลักดังนี้:

1. Requirement ใหม่ในเอกสารนี้มีสิทธิ์เหนือกว่า Flow หรือ Model ของระบบเดิมที่ขัดแย้งกัน
2. ระบบเก่าที่ถูกแทนที่ด้วย Plate-based ต้องไม่ถูกนำกลับมาเป็น Business Flow หลัก
3. Core System ต้องทำงานครบและสอดคล้องกันก่อนเริ่ม Marketplace
4. เมื่อมีการเปลี่ยน Business Rule ต้องตรวจสอบผลกระทบต่อ Database, Controller, Service, View, Test และ Scheduler ที่เกี่ยวข้องทั้งหมด
5. การแก้ระบบควรทดสอบทั้ง Happy Path และ Edge Case ตาม Requirement ไม่ใช่ตรวจเฉพาะว่า Route เปิดได้
6. เมื่อมี Feature ใหม่เข้ามาแทน Feature เดิม ต้องย้าย Dependency ไปยัง Feature ใหม่และลบ Legacy ที่ถูกแทนที่ ไม่ให้มี Business Flow ซ้ำซ้อนสองชุด
7. Auto Check-in และ Auto Check-out เป็น Flow หลัก แต่ต้องคง Manual Check-in และ Manual Check-out เป็น Fallback ที่ได้รับอนุญาตตามสิทธิ์และเงื่อนไขของระบบ
8. ทุก Payment ที่เปลี่ยนสถานะเป็น `paid` ต้องระบุผู้ยืนยันและเวลาที่ตรวจสอบได้
9. Logs ต้องครอบคลุมผู้ใช้งานทุก Role และเหตุการณ์สำคัญของระบบตามข้อมูลที่ระบบสามารถเก็บได้
